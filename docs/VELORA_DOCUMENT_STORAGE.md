# Velora MERN - Private document storage, API and recovery (Part 4)

Private discharge documents for one recovery episode. MongoDB holds **metadata only**; the bytes
live in encrypted private storage addressed by an **opaque UUID key**. No public URL, no path and no
object-store bucket is ever recorded, returned or logged.

> A document status of `ready` means the file was **technically accepted for later review**. It never
> means clinically approved, and no part of this subsystem makes a clinical judgement.

## 1. External service gate (control #22)

**No external provider is selected or called.** AWS S3, Cloudinary, Firebase, an antivirus service,
an OCR service and a queue provider remain **DISCLOSED / NOT SELECTED**. Until the owner chooses one,
the shipped provider is a local encrypted filesystem provider behind a provider-neutral interface.

| Provider | Purpose | API key name | Env var | Location | Data sent | Region / retention | Cost |
|---|---|---|---|---|---|---|---|
| *none* (local encrypted filesystem) | store encrypted document bytes | n/a | `DOCUMENT_STORAGE_ROOT`, `DOCUMENT_ENCRYPTION_KEY` | server only (`server/src/services/documentStorage.js`) | nothing leaves the host | host disk, operator-controlled retention | none |

If a provider is added later it must be disclosed first (provider, purpose, key name, env var,
backend/frontend location, data sent, region/retention, cost/rate) and must implement the same
interface in section 3 without changing callers.

## 2. Environment (fail-closed, validated at startup)

| Variable | Rule | Local value |
|---|---|---|
| `DOCUMENT_STORAGE_ROOT` | **absolute** path, **outside the repository** and any web root; a relative or in-repo path fails startup | an absolute path outside the checkout, e.g. `<home>/velora-documents` |
| `DOCUMENT_ENCRYPTION_KEY` | base64 of exactly 32 bytes; **separate** from `MFA_ENCRYPTION_KEY` and `SESSION_PEPPER` | generated by `npm run gen:env` |
| `DOCUMENT_MAX_BYTES` | hard upload ceiling, default and CI value `10485760` (10 MiB) | `10485760` |
| `DOCUMENT_PARSER_TIMEOUT_MS` | wall-clock limit for one validation worker | `3000` |
| `DOCUMENT_PARSER_MEMORY_MB` | V8 heap cap for the worker | `128` |
| `DOCUMENT_PARSER_CONCURRENCY` | workers that may run at once | `2` |
| `DOCUMENT_PARSER_QUEUE_MAX` | waiting uploads before the API answers `503` | `8` |

The storage root and its key are validated **as a pair**: a root without its own key would store
plaintext, so both are required. `MONGODB_URI`, the pepper and the key are server-only and never
reach the browser.

## 3. Provider-neutral storage interface

`server/src/services/documentStorage.js` exports exactly one active provider and a narrow API:

| Method | Contract |
|---|---|
| `newStorageKey()` | returns a fresh opaque UUID |
| `put(key, plaintext)` | encrypts and writes **exclusively** (`wx`); fails if the object exists |
| `get(key)` | decrypts and returns the plaintext bytes; fails on tamper |
| `stat(key)` | metadata only, or `null` for a non-regular file |
| `remove(key)` | deletes one object |
| `listKeys()` | the stored object keys (used **only** by reconciliation) |

Implementation guarantees of the shipped local provider:

- key shape is re-validated (`^[0-9a-f]{8}-...$`) before any path is built, so `..`, separators,
  absolute paths and filenames can never form an object path;
- layout is `<root>/objects/<first two hex>/<uuid>.bin`; directories `0700`, files `0600` where the
  platform supports it;
- reads `lstat` first and refuse anything that is not a regular file (no symlink following);
- AES-256-GCM with a random 12-byte IV and a 16-byte authentication tag, envelope
  `"VD1" || iv || tag || ciphertext`; a tampered object fails decryption instead of returning bytes.

`documentService` never touches the filesystem: it only calls this interface.

## 4. Validation pipeline (bounded and isolated)

Order of checks for every upload:

1. **Authorize first** (`requireDocumentUploadAccess`): session, clinic, active care-team assignment,
   episode state, rate limit - all before a single body byte is read.
2. **Bounded body read** (`boundedBody`): hard cap `DOCUMENT_MAX_BYTES`; a longer body is destroyed
   mid-stream and answered with `413`.
3. **Isolated worker** (`workers/documentParser.js` under `services/documentValidator.js`): a
   `worker_threads` thread with a wall-clock timer, `resourceLimits` heap cap, concurrency limit,
   bounded queue, and an environment reduced to `NODE_ENV` - **no application secrets**.
4. **Filename / extension / declared type / magic bytes / actual parsed type / empty file /
   trailing unexpected data**, then the structural PDF and image rules.

Refused (structural rejection, metadata row recorded as `rejected`, **no bytes stored**):
`PDF_ENCRYPTED`, `PDF_ACTIVE_CONTENT` (JavaScript, actions, launch, rich media, submit/import),
`PDF_ATTACHMENT` (embedded files), `PDF_FORM` (AcroForm/XFA), `PDF_EXTERNAL_REF` (GoToR/GoToE/URI),
`PDF_MALFORMED`, `PDF_TRAILING_DATA`, `PDF_TOO_MANY_PAGES`, `PDF_TOO_MANY_OBJECTS`,
`PDF_STREAM_TOO_LARGE`, `IMAGE_MALFORMED`, `IMAGE_PIXEL_BOMB`, `IMAGE_MULTIFRAME`.

Refused without any row (`invalid`): `EMPTY`, `TOO_LARGE`, `BAD_FILENAME`, `UNSUPPORTED_TYPE`,
`TYPE_MISMATCH`.

Kept but held (`quarantined`, encrypted, never downloadable): `PARSER_TIMEOUT`, `PARSER_ERROR` -
the parser could not reach a verdict, so an operator decides.

Only stable codes ever leave the process. Parser paths, stacks and diagnostics never do.

> **No antivirus certification is claimed.** These checks are structural and technical only.

## 5. Statuses, duplicates and retries

| Status | Meaning | Downloadable |
|---|---|---|
| `uploading` | metadata written, object write in flight | no |
| `ready` | technically accepted for later review | **yes** |
| `rejected` | structurally refused; no bytes stored | no |
| `quarantined` | verdict inconclusive; bytes held privately for an operator | no |
| `failed` | the stored copy could not be read or verified | no |

- **Unique episode + checksum** (`{episode, sha256}`) and **unique opaque storage key** are database
  indexes, so a byte-identical duplicate can never be stored twice even under parallel requests.
- A duplicate of a **live** document (`uploading`/`ready`/`quarantined`) returns the existing row
  with `duplicate: true` and writes no second object.
- Re-uploading a corrected file after a `rejected`/`failed` row **reuses** that row (same key) rather
  than piling up rows.
- **Safe retry:** if a previous attempt wrote the object but failed before finalising the row, a retry
  cannot overwrite it (`put` is exclusive and fails). The row is marked `failed`, and the orphaned
  object is removed by the reconciliation command (section 7) - never silently overwritten.

## 6. Atomicity limits (documented, not hidden)

MongoDB metadata and the encrypted object are **not one transaction**:

```
insert metadata (uploading)  ->  write encrypted object  ->  set status ready
```

- Crash after the insert, before the write: a stale `uploading` row with no object.
- Crash after the write, before `ready`: an object with an `uploading` row.
- A manual or restored file change: an object that no longer matches its checksum.

Every one of those states is **detected and reported** by reconciliation, and none of them ever
serves bytes without a fresh authorization, decryption, byte-size check and SHA-256 check.

## 7. Reconciliation and recovery

```bash
npm run documents:reconcile -w server                              # dry run (default, changes nothing)
npm run documents:reconcile -w server -- --apply --operator you@clinic.example
```

The dry run prints a report: live metadata rows, stored objects, missing objects, unreadable objects,
integrity mismatches and orphan objects (keys with no live row). `--apply` refuses to run without an
explicit `--operator`, and every repair it performs is written to the audit log:

| Finding | Applied action | Audit action |
|---|---|---|
| object missing / unreadable / checksum mismatch | row set to `failed` | `document.reconciled.failed` |
| object with no live metadata row | object removed | `document.reconciled.orphan-removed` |

### Recovery runbook

1. **Back up and restore as ONE set.** MongoDB metadata + the encrypted objects + the document key
   (plus `SESSION_PEPPER`/`MFA_ENCRYPTION_KEY` for sessions). Objects without the document key are
   cryptographically unrecoverable (AES-256-GCM); the key without the objects restores nothing.
2. Restore the three parts together, then run the **dry run** and read the report before changing
   anything.
3. Expect drift if a restore was partial: metadata rows whose objects are missing show up as
   `missing`, and restored objects with no row as `orphan`.
4. Apply with an explicit operator attribution, so the repair is attributable.
5. Re-upload anything marked `failed` (the corrected file reuses the same row) and confirm `ready`.
6. Confirm no `uploading` rows remain: the dry run lists none once every interrupted attempt has been
   finalised or failed.

## 8. HTTP contract

All paths are relative to the API base (`/api`). Sessions are cookie-based; every mutation requires
the CSRF header. Responses are `Cache-Control: no-store, private, max-age=0`, and the original
filename only ever travels in a header (request) or in the `Content-Disposition` attachment header
(response) - never in a URL, a query string or a routine log line.

| Method | Path | Who | Notes |
|---|---|---|---|
| `POST` | `/episodes/:episodeId/documents` | assigned care-team member, `draft` episode | body = raw file bytes; `Content-Type` = declared type; `X-Document-Filename` = percent-encoded display name |
| `GET` | `/episodes/:episodeId/documents?page=&limit=` | team member or the patient owner | paginated metadata list |
| `GET` | `/episodes/:episodeId/documents/:documentId` | team member or the patient owner | metadata detail |
| `GET` | `/episodes/:episodeId/documents/:documentId/download` | team member or the patient owner | `ready` only |
| `GET` | `/patient/me/episodes/:episodeId/documents[?page=&limit=]` | the owning patient | same list, ownership-scoped |
| `GET` | `/patient/me/episodes/:episodeId/documents/:documentId` | the owning patient | metadata detail |
| `GET` | `/patient/me/episodes/:episodeId/documents/:documentId/download` | the owning patient | `ready` only |

Upload response `201`:

```json
{ "document": { "id": "...", "filename": "discharge-summary.pdf", "mediaType": "application/pdf",
  "byteSize": 24123, "sha256": "…", "status": "ready", "rejectionCode": null,
  "technical": { "pages": 2, "width": null, "height": null }, "readyForReview": true,
  "uploadedAt": "…", "updatedAt": "…" }, "duplicate": false }
```

The document object never contains the storage key, a filesystem path or a URL.

| Status | When |
|---|---|
| `400` | refused file (`EMPTY`, `PDF_ACTIVE_CONTENT`, `TYPE_MISMATCH`, …) or invalid query |
| `401` | no valid session |
| `403` | not an active team member (write), or an administrator (clinical reads) |
| `404` | the episode is not visible to the caller (uniform, no existence leak) |
| `409` | episode is not `draft`, or the document is not `ready` for download |
| `413` | body exceeds 10 MiB |
| `415` | declared type is not PDF/JPEG/PNG |
| `429` | upload/read/download limit reached |
| `503` | parser concurrency and queue are saturated - retry |

Limits are separate per operation: upload `20/hour`, download `120/hour`, metadata read `600/hour`
per authenticated user.

Download headers: `Content-Type` (allowlisted type), `Content-Length`, `Content-Disposition:
attachment` with RFC 6266 encoding, `X-Content-Type-Options: nosniff`,
`Content-Security-Policy: default-src 'none'; sandbox`, `Cross-Origin-Resource-Policy: same-origin`,
and `Cache-Control: no-store`.

## 9. Screens

Staff: episode detail -> **Documents** tab -> `choose -> review -> upload -> result`, plus the
paginated list, the technical-status summary, per-document status notes and an authenticated blob
download. Patients see the same list and download for their own episode, read-only ("Only your care
team can upload documents."). A denied read clears the list and shows a safe sentence instead of
stale metadata. Object URLs are revoked after the download starts.
